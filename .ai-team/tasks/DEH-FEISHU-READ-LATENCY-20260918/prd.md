# DEH-FEISHU-READ-LATENCY-20260918 产品需求文档

## 1. 产品目标与目标用户价值

### 1.1 产品目标

在正式数据源继续使用飞书多维表格的前提下，消除同表重复实时读取、短缓存失效和复合接口分段等待。本期性能硬门槛覆盖首屏 P0 五项 COM-001、COM-002、COM-005、WB-001、WB-002：热态 p95 不超过 2 秒；其余 60 项正式读取操作本期执行正确性、权限隔离、失效闭环与无 504 回归，不据此宣称全部 65 项均已达到 2 秒。后续若要把 2 秒硬门槛扩大到其余操作，必须基于本期统一观测结果另行批准范围。

本任务不承诺飞书上游实时请求本身必然小于 2 秒。1–2 秒目标通过服务端共享缓存、预热、后台刷新、读取合并、并行执行与精确失效实现。

### 1.2 目标用户价值

- 数智产品展厅 Web 用户：打开 P0 首屏时，在热态 2 秒内看到可用内容；真正冷启动时在 2 秒内看到明确的首次同步状态，不再等待到 504。
- 验收人员：可以通过统一的真实环境证据区分热态命中、冷态同步、陈旧快照、强一致读取与飞书上游耗时，能够重复验证性能结论。
- 运维与开发人员：可以确认慢请求来自缓存未命中、排队、上游读取或复合接口依赖阶段，避免只靠延长超时掩盖问题。

## 3. 范围边界

### 3.1 本期范围内

1. 将同一飞书表的完整或可合并读取归一为共享数据源，避免因字段组合不同重复访问飞书；相同在途请求只执行一次。
2. 建立服务端共享缓存与后台刷新机制：
   - 新鲜快照直接返回；
   - 过期但仍在允许降级窗口内的快照先返回并单飞后台刷新；
   - 多个并发请求不得重复触发相同刷新；
   - 服务启动后按 P0 页面依赖执行受控预热；不把业务快照持久化到磁盘、数据库或外部缓存。
3. 并行化没有数据依赖关系的表读取和投影计算，同时保留最多 8 路上游安全并发限制，不通过无限并发换取表面速度。
4. 为缓存键加入租户、数据范围、身份或权限指纹、表/投影版本等必要隔离维度，防止越权复用。
5. 写入成功后精确失效对应表、聚合投影和受影响用户范围缓存；强一致例外不得返回陈旧状态。
6. 响应中提供可判断数据状态的元信息，包括数据来源时间、是否陈旧、是否正在后台刷新；不得暴露密钥、令牌、Cookie 或未脱敏个人信息。
7. 对真实飞书环境完成冷态、热态、并发、失效和上游失败降级验证，并产出可复验、已脱敏的性能证据。
8. 覆盖全部 65 个正式读取 operation：P0 五项执行 p95≤2 秒门槛，其余 60 项执行无 504、正确性、权限隔离和写后失效门槛；未在矩阵分类的新增 operation 默认禁用缓存且不得计入验收。

### 3.2 本期范围外

1. 不把正式数据源替换为本地演示数据、静态 JSON 或无法追溯来源的假数据。
2. 不承诺飞书 Open API 的每一次实时上游调用必然小于 2 秒。
3. 不通过单纯放宽客户端、服务端或代理超时时间来判定性能完成。
4. 不缓存、记录或输出飞书凭据、访问令牌、Cookie 与未脱敏个人信息。
5. 不修改非 `TEST_` 正式业务数据，不借性能验证执行无关正式数据写入。
6. 不改变审批、权限和写入业务规则；不把需要强一致的数据改为无限陈旧读取。
7. 不执行合并、部署或发布。

### 3.4 冷启动快照契约：不持久化

本期明确选择“不持久化业务快照”方案：

1. **介质**：缓存只存在于服务进程内存，不写入磁盘、数据库、Redis、浏览器存储或日志。
2. **真正冷启动**：进程启动、重启、崩溃恢复或新实例扩容后，视为没有任何业务快照；所有可缓存 operation 在 2 秒内返回“首次同步中”的可恢复状态，由后台预热。不得把预热过程称为已有冷态快照。
3. **访问控制**：缓存仅由服务端读取服务访问；缓存键不得包含明文令牌、Cookie、手机号或邮箱。用户/管理缓存键使用租户标识、不可逆身份指纹、不可逆权限指纹、数据范围指纹和请求投影版本。
4. **版本**：每个缓存项必须携带 `snapshotSchemaVersion`、`sourceContractHash`、`cachePolicyVersion`、`sourceUpdatedAt`、`createdAt`、`freshUntil`、`staleUntil`。任一版本或权限指纹变化即视为未命中并淘汰旧项。
5. **过期**：达到 `freshUntil` 后只能按 SWR 规则作为陈旧响应；达到 `staleUntil` 后立即不可读并删除。
6. **淘汰**：采用进程内 LRU，最多 1,000 项或 128MiB，任一上限先达到即从最久未使用项开始淘汰；权限变更、source contract 变化、部署新版本和写后失效优先于 LRU。
7. **加密**：因不存在静态持久介质，本期无“静态快照加密”对象；传输仍沿用现有 HTTPS。未来若引入跨进程持久快照，必须另立高风险任务定义加密、密钥、保留期和运维责任，不得在本任务中临时加入。

写后失效的成功与失败语义固定如下：

1. 飞书业务写入成功后，服务端必须先建立对应资源族的 dirty/version fence，再清除相关缓存，最后才能返回普通成功。
2. 若缓存清除失败但 dirty fence 已建立，相关读取必须绕过缓存强制回源；写接口不得返回普通成功，而返回可重试的“业务已提交、缓存同步待修复”语义，并携带同一 `traceId` 与幂等结果，避免客户端重复创建业务记录。
3. 若 dirty fence 也无法建立，相关缓存族立即进入进程级 fail-closed 状态并禁止读取旧快照；写接口不得确认成功，必须告警并进入人工/自动重放失效流程。
4. 当前 36 个写入口均已有幂等键治理；重试必须复用原幂等结果，只重做失效，不重复业务写入。
5. 不自动回滚已由飞书确认成功的业务写入，除非具体业务合同另有安全补偿；本任务的补偿只包括重放失效、强制回源和恢复缓存可读状态。
6. 固定可观测字段为：`trace_id`、`operation_id`、`idempotency_key_hash`、`business_commit_status`、`dirty_fence_status`、`cache_invalidation_status`、`affected_cache_families`、`affected_cache_key_count`、`fallback_mode`、`reconcile_status`。不得记录幂等键明文或敏感业务内容。

### 3.8 固定性能观测与样本口径

每个读取 trace 必须产生同一 `trace_id` 关联的服务端摘要与分段 span，固定字段如下：

| 字段 | 定义 |
| --- | --- |
| `total_ms` | 服务端收到请求至响应体完成序列化的墙钟耗时 |
| `cache_status` | `fresh_hit`、`stale_hit`、`miss_syncing`、`miss_blocking`、`bypass_strong` 之一 |
| `limiter_wait_ms` | 此 trace 关键路径上等待飞书并发限流器的墙钟耗时；并行调用另记录 `limiter_wait_sum_ms` |
| `token_wait_ms` | 此 trace 等待租户令牌缓存/在途获取的墙钟耗时，令牌已命中为 0 |
| `feishu_network_ms` | 此 trace 从首个实际上游发送至最后一个上游响应完成的墙钟区间；并行调用另记录 `feishu_network_sum_ms` |
| `feishu_call_count` | 实际发送到飞书的 HTTP 请求总数 |
| `pagination_call_count` | 其中分页 records 请求总数；每一页计 1 |
| `projection_ms` | 飞书数据到业务响应投影、过滤、排序和聚合耗时 |
| `serialization_ms` | 业务响应对象序列化耗时 |
| `refresh_ms` | 后台刷新从创建到完成的墙钟耗时；非刷新请求为 0 |
| `operation_id` / `cache_policy` | 当前 operation 与本 PRD 策略代码 |
| `source_contract_hash` / `snapshot_schema_version` | 数据合同与快照版本；只记录不可逆摘要 |

采样规则固定为：

1. 真实环境记录服务版本、源码版本、网络位置、代理模式、飞书 Base 的合同哈希、每张依赖表记录量和 `sourceUpdatedAt`；不得记录表内容和凭据。
2. 每个 P0 operation 先执行 3 次不计样本的预热；然后执行 30 次顺序新鲜热态调用，再执行 5 批×8 路并发共 40 次新鲜热态调用。
3. p95 使用 nearest-rank：升序样本的第 `ceil(0.95×N)` 个值。错误响应不得从 504 计数中剔除；只有 `fresh_hit` 且响应合同正确的样本进入 P0 新鲜热态 p95。
4. `stale_hit`、`miss_syncing`、`bypass_strong` 和错误响应分别统计，不得混入新鲜热态 p95。强一致 operation 单列 `total_ms` 与全部阶段计时，不宣称 2 秒达标。
5. 冷启动至少执行 5 次真正进程重启；每次确认内存缓存为空且无持久快照，并验证 2 秒内返回 `miss_syncing`，随后后台预热能完成且下一次读取转为 `fresh_hit`。
6. 并发场景必须同时给出 `limiter_wait_ms` p50/p95/max、`token_wait_ms`、`feishu_network_ms`、实际上游调用数和分页数，用以判断慢请求是否来自排队、令牌、网络、分页或投影。

## 4. 主用户流程

### 4.1 普通可缓存只读流程

1. **入口**：已授权用户进入工作台、应用中心或其他使用正式飞书数据的 Web 页面。
2. **请求**：页面并发发起所需只读接口，服务端按统一资源键判断缓存状态。
3. **决策点 A — 新鲜快照存在**：在 2 秒内直接返回快照，标记 `dataStale=false`，必要时按刷新阈值异步预刷新。
4. **决策点 B — 快照已过期但仍在允许降级窗口内**：在 2 秒内返回最近一次成功快照，标记 `dataStale=true` 和 `sourceUpdatedAt`，仅启动一次后台刷新；同资源的并发请求复用该刷新。
5. **决策点 C — 无可用快照**：在 2 秒内返回明确的“首次同步中/可重试”状态，不让页面阻塞至 504；后台执行受控真实同步。
6. **刷新完成**：更新共享快照和来源时间，后续请求返回新数据；页面可自动重新拉取或由用户重试，不出现无限转圈。
7. **结果**：用户看到可用数据或明确、可恢复的同步状态；系统留下脱敏的命中类型、耗时与刷新证据。

### 4.2 写入后的精确失效流程

1. 用户完成已授权写入。
2. 写入成功后，服务端按受影响表、聚合投影、租户、身份与权限范围精确失效缓存。
3. 写入结果确认与审批状态查询走强一致路径，不返回失效前快照。
4. 后续普通只读请求重新构建快照，未受影响资源继续命中缓存，避免全量清空造成冷启动风暴。

### 4.3 上游失败降级流程

1. 后台刷新遇到飞书超时、限流或暂时不可用。
2. 若存在仍在允许降级窗口内的合规快照，接口在 2 秒内返回该快照并明确标记陈旧；记录脱敏错误类型和追踪标识。
3. 若不存在可用快照，接口在 2 秒内返回可恢复错误/同步状态，不返回伪造数据，也不等待到 504。
4. 后续请求按受控退避重试，避免所有页面同时击穿飞书。

## 5. 状态清单

| 状态 | 触发条件 | 用户可见行为 | 系统行为 |
| --- | --- | --- | --- |
| 成功 / 新鲜 | 新鲜共享快照存在 | 2 秒内展示数据，不阻塞页面 | `dataStale=false`，返回 `sourceUpdatedAt` |
| 成功 / 陈旧刷新中 | 快照过期但仍在降级窗口内 | 2 秒内展示最近数据，可提示“数据更新中” | `dataStale=true`，单飞后台刷新 |
| 首次同步中 | 服务冷启动且无任何合规快照 | 2 秒内展示明确同步状态与可重试入口，不无限转圈 | 返回可恢复状态，后台受控同步 |
| 加载中 | 请求尚未在 2 秒内完成 | 页面显示明显、局部或全局一致的加载反馈 | 不禁用无关操作；2 秒内必须转入成功、同步中或错误状态 |
| 空数据 | 飞书成功返回且业务数据确实为空 | 展示业务空状态，不展示接口错误 | 缓存空结果并记录来源时间，避免反复击穿上游 |

| 上游错误且不可降级 | 无快照或快照超过最大陈旧窗口 | 展示明确错误、追踪标识和重试入口 | 不返回伪造数据，不泄露上游敏感信息 |
| 禁用 | 接口或页面功能按配置禁用 | 按既有禁用态展示，不触发飞书读取 | 不以缓存绕过禁用规则 |

| 强一致读取 | 审批状态、写后确认、权限确认 | 展示明确“正在查询最新状态”反馈 | 绕过陈旧快照；记录真实上游耗时，不伪造 2 秒结果 |

## 6. 明确非目标 / 禁止事项

1. 不把所有接口简单改成长缓存而忽略数据新鲜度、写后失效和身份隔离。
2. 不以返回旧数据但不标记陈旧的方式达成 2 秒指标。
3. 不让同一资源在并发缓存未命中时产生多次相同飞书请求。
4. 不把最多 8 路上游并发限制提升为不受控并发。
5. 不把审批状态、写入结果确认或权限确认纳入可陈旧缓存。
6. 不把首次同步中的 202/可恢复状态统计成“新鲜数据成功”，性能证据必须分开标注命中类型。
7. 不在日志、缓存键、证据文件或错误消息中保存明文凭据、访问令牌、Cookie、手机号、邮箱等未脱敏信息。
8. 不在本任务中执行部署、发布、合并或非 `TEST_` 正式业务数据修改。

## 8. 验收标准

### AC-01：P0 热态响应时间

**Given** 租户令牌有效、服务进程已启动且 P0 代表接口所需共享快照已经建立，  
**When** 按 3 次预热、30 次顺序样本和 5 批×8 路并发样本调用 COM-001、COM-002、COM-005、WB-001、WB-002，  
**Then** 每个接口的顺序与并发新鲜热态 p95 均不超过 2,000 毫秒，且 504 数量为 0。

### AC-02：浏览器可见性能

**Given** 用户已完成授权且 P0 页面处于热态，  
**When** 浏览器进入对应页面并发发起 Fetch/XHR，  
**Then** P0 代表接口的浏览器侧 p95 不超过 2,000 毫秒，页面在 2 秒内展示可用内容，且不得用隐藏请求失败或静态假数据替代正式结果。

### AC-03：65 项分级清单完整性

**Given** operation registry 中存在 65 个 read operation，  
**When** 自动化核对本 PRD 的覆盖矩阵与运行时读取计划，  
**Then** 矩阵恰好覆盖 65 个唯一 ID，P0-2S=5、S-COR=9、R-COR=51，无遗漏、重复或未分类项；只有 P0-2S 可用于 2 秒完成声明。

### AC-04：真正冷启动统一同步态

**Given** 服务进程刚启动或重启，且按契约不存在持久化业务快照，  
**When** 用户发起任一可缓存只读请求，  
**Then** 接口在 2,000 毫秒内返回 `miss_syncing` 的明确、可恢复首次同步状态和追踪标识，不返回 504、不伪造数据；后台预热完成后下一次读取转为 `fresh_hit`。

### AC-05：同表不同字段读取合并

**Given** 多个并发接口读取同一飞书表但请求字段组合不同，  
**When** 这些请求落在同一数据版本和权限范围内，  
**Then** 服务端复用同一份可满足请求的共享表快照或同一在途读取，不因字段组合不同重复访问飞书；证据需显示逻辑请求数与实际上游调用数。

### AC-06：在途请求单飞

**Given** 某资源缓存未命中且正在刷新，  
**When** 8 个并发请求同时读取该资源，  
**Then** 只产生 1 个该资源的后台刷新任务，其余请求复用在途结果或合规快照，不形成 8 次相同飞书读取。

### AC-07：复合接口并行化

**Given** 一个复合接口需要读取多个彼此无依赖的飞书表或投影，  
**When** 服务端构建响应，  
**Then** 无依赖阶段并行执行，有依赖阶段才顺序执行；实际飞书并发峰值不超过 8，并以同一 `trace_id` 输出 `total_ms`、`limiter_wait_ms`、`token_wait_ms`、`feishu_network_ms`、`feishu_call_count`、`pagination_call_count`、`projection_ms`、`serialization_ms` 和 `cache_status`。

### AC-08：数据新鲜度与 SWR

**Given** 普通可缓存快照超过刷新间隔但未超过最大陈旧窗口，  
**When** 用户再次读取，  
**Then** 接口在 2,000 毫秒内返回陈旧标记明确的最近快照，同时只触发一次后台刷新；刷新成功后下一次读取返回新来源时间和 `dataStale=false`。

### AC-09：空数据缓存

**Given** 飞书成功返回业务空集合，  
**When** 用户重复访问相同范围，  
**Then** 页面展示空状态，服务端在刷新间隔内复用该空结果，不因“0 条”被误判为未命中而重复访问飞书。

### AC-10：写后精确失效

**Given** 36 个写 operation 中任一写入成功并影响指定表、投影或用户范围，  
**When** 写入流程准备返回成功，  
**Then** 必须已建立 dirty/version fence 并完成矩阵指定的精确失效；下一次相关读取不得返回写入前快照，未受影响缓存仍可命中，且 36 个写 ID 均能被自动化映射到至少一个明确失效结论或“无缓存消费者”结论。

### AC-11：强一致例外

**Given** 请求属于审批状态、写入结果确认或权限确认，  
**When** 用户查询最新状态，  
**Then** 服务端绕过陈旧快照并读取真实最新状态；页面展示清晰请求中/失败/重试状态，证据独立记录真实上游耗时，不把陈旧缓存结果计入 2 秒热态达标。

### AC-11A：失效失败注入

**Given** 飞书业务写入已成功，测试注入缓存清除失败，  
**When** 服务端处理失效结果，  
**Then** 写接口不得返回普通成功；相关缓存族进入强制回源或 fail-closed 状态，旧快照不可读，并记录同一 trace 的业务提交、dirty fence、失效和重放状态；使用同一幂等键重试时只重做失效，不重复创建或修改业务记录。

### AC-12：权限与隐私隔离

**Given** 两个不同租户、身份、数据范围或权限指纹的用户读取同一业务资源，  
**When** 服务端查找共享缓存，  
**Then** 不发生跨范围缓存命中；401/403 不得回退为其他用户的缓存数据，日志与证据中不得出现凭据、令牌、Cookie 或未脱敏个人信息。

### AC-13：飞书失败降级

**Given** 飞书出现超时、限流或暂时不可用，  
**When** 请求存在仍在最大陈旧窗口内的合规快照，  
**Then** 接口在 2,000 毫秒内返回标记为陈旧的快照并记录脱敏追踪信息；若无合规快照，则在 2,000 毫秒内返回可恢复错误/同步状态，不等待到 504。

### AC-14：缓存过期上限

**Given** 最近进程内快照已超过策略规定的最大陈旧窗口，或 snapshot schema、source contract、cache policy、租户/身份/权限指纹任一变化，  
**When** 飞书刷新失败，  
**Then** 服务端淘汰该快照且不得作为正常数据返回，必须进入明确错误/同步状态并提供重试路径；LRU 达到 1,000 项或 128MiB 上限时同样按契约淘汰。

### AC-15：全量回归与证据

**Given** 性能实现完成，  
**When** 在真实飞书环境执行冷态、热态、8 路并发、写后失效、权限隔离和上游失败降级验证，  
**Then** 产出包含环境/源码版本、合同哈希、依赖表记录量、样本数、nearest-rank p50/p95/max、缓存状态及全部固定阶段计时的脱敏证据；`fresh_hit`、`stale_hit`、`miss_syncing`、`bypass_strong` 分别统计；全部 65 个 read operation 不得出现 504、错误授权、跨身份数据串用或合同回归。

### AC-16：非 P0 不虚假宣称性能完成

**Given** 某 operation 在矩阵中为 R-COR 或 S-COR，  
**When** 它通过正确性和无 504 回归但耗时仍高于 2 秒，  
**Then** 本任务只能报告该 operation“正确性/稳定性通过”，不得报告“2 秒性能通过”；其阶段计时证据用于决定后续性能任务范围。
