# UX Handoff — 正式飞书读取 1–2 秒状态闭环

## 1. 目的、批准依据与设计边界

本交接把已批准的 [PRD](../prd.md) 转换为任务 `DEH-FEISHU-READ-LATENCY-20260918` 的 Web 交互合同。范围批准记录见 [task.json](../task.json) 与 [decision log](../decision-log.md)：五个 P0 首屏 operation `COM-001`、`COM-002`、`COM-005`、`WB-001`、`WB-002` 的新鲜热态 p95 不超过 2 秒；其余 60 项本期只承诺合同正确、权限隔离、失效闭环与 0 个 504；真正冷启动在 2 秒内进入可恢复的首次同步状态；强一致读取不返回陈旧快照。

本文件只定义用户如何理解数据新鲜度、等待、恢复、权限和写后失效结果，以及键盘、焦点、live announcement 和响应式 Web 行为。它不选择颜色、字体、间距、图标、组件外观或其他视觉方向，不改变缓存 TTL、身份隔离、业务权限、写入、并发、发布和证据规则，也不构成设计批准或开发放行。

## 3. 平台声明与信息架构

### 3.1 平台

**仅 Web。** `task.json` 声明 `platforms=["web"]`、Vue Web，未声明 uni-app 或原生移动端。宽屏和窄屏 Web 使用同一业务状态、文案语义、键盘顺序与恢复规则；窄屏只重排信息，不产生移动端专属流程。

### 3.2 状态信息层级

数据状态按以下层级归属，避免一个慢 operation 锁住整页：

1. **入口/会话层**：只负责登录确认与 authentication-required；不把登录失败混同 permission-denied。
2. **页面汇总层**：并发初始读取时只给一次简短汇总，例如“正在加载工作台数据”；不得逐条播报五个 P0 请求。
3. **operation 所有者区域**：新鲜、陈旧、首次同步、空、失败、权限和重试均归属产生该内容的区域；`aria-busy` 也只放在该区域。
4. **动作结果层**：强一致查询和写后失效失败紧邻发起动作或状态结果，不以全局“已成功”覆盖真实状态。

### 3.3 P0 operation 与现有可见区域

| Operation | 现有所有者区域 | 本任务中的状态所有权 |
| --- | --- | --- |
| `COM-001` | 顶部当前用户信息、工作台 hero 身份/问候 | 只更新身份相关内容；无身份结果时不得保留另一人的姓名、组织或权限暗示。 |
| `COM-002` | 主导航、侧栏及个性化菜单 | 只更新受权限控制的导航；加载/失败时保留品牌、当前安全路由和跳到主内容，不展示未经确认的菜单。 |
| `COM-005` | 场景化搜索和依赖字典的筛选项 | 字典不可用时禁用依赖字典的选择；不依赖字典的自由文本输入仍可用。 |
| `WB-001` | hero 数据上下文、应用类型概览、热门应用初始推荐、培训课堂、公告通知、我的使用统计 | 各面板显示自己的状态，但共享同一 `WB-001` 请求；任一面板发起重试时，其他重复重试入口同步忙碌。 |
| `WB-002` | 热门应用推荐中的查询/场景筛选结果 | 仅最新查询拥有结果；新请求期间保留最近一次仍合规的可读结果，并在该区域标记其新鲜度。 |

其他 60 项读取沿用同一状态合同，但不显示或暗示“2 秒性能已达标”。

## 4. 元数据到内容语义的唯一映射

### 4.1 字段语义

| 字段 | 用户内容语义 | 不得表达为 |
| --- | --- | --- |
| `dataStale=false` | 返回内容位于当前策略的新鲜窗口内。常规首屏直接展示内容；无需额外“实时”成功徽标。 | “飞书中的每一次业务变化均已实时同步”或“当前页面永不过期”。 |
| `dataStale=true` | 当前展示的是同租户、同身份/权限范围内最近一次成功快照，已超过新鲜窗口，但仍在 PRD 允许的陈旧窗口内。 | 未加说明的正常数据、跨身份备用数据、超过 `staleUntil` 的数据。 |
| `sourceUpdatedAt` | **这份返回快照最近一次成功从正式源建立/更新的时间**。显示为“数据更新于 YYYY-MM-DD HH:mm”；按用户本地时区格式化，保留机器可读 datetime。 | 浏览器请求时间、后台刷新开始时间、用户写入时间，或无依据的“实时同步”。 |
| `refreshing=true` | 这份快照保持可读，同时相同资源已有一次受控后台刷新正在进行；内容提示“正在获取最新数据”。 | 页面仍在等待才能使用、每位用户各自触发刷新、数据一定有变化。 |
| `refreshing=false` | 当前没有已确认在途刷新。与 `dataStale=false` 组合时无需额外提示；与 `dataStale=true` 组合时必须说明“暂未更新”，并依据服务端 retryability 提供重试或等待信息。 | “数据已是最新”——除非 `dataStale=false`。 |

`sourceUpdatedAt` 缺失时不得显示虚构时间。新鲜内容可不展示时间；陈旧内容必须显示已有时间，若合同异常导致时间缺失，则使用“更新时间暂不可用”的安全文案并保留陈旧提示，该合同缺口要进入 QA 证据。

### 4.2 operation 到页面聚合规则

1. 分区状态以 `sectionRecords[operationId]` 为准；页面级 `dataStale` 只能作为“至少一个可见区域陈旧”的汇总，不能让所有区域统一误标为陈旧。
2. 同一区域依赖多个 operation 时，只要任一已展示内容为陈旧，区域就显示陈旧说明，并使用该区域**最早的相关 `sourceUpdatedAt`**作为保守的“数据更新于”时间；不得用较新的无关 operation 时间掩盖较旧数据。
3. `refreshing` 为区域依赖项的逻辑 OR。刷新完成后，如果内容版本或 `sourceUpdatedAt` 改变，原位更新；没有变化也结束“正在获取最新数据”。
4. `dataStale=true` 不等于 error。内容、导航和非冲突操作保持可用；只在用户动作必须依赖最新状态时转入强一致流程。
5. 达到最大陈旧窗口、版本/合同/权限指纹变化或 fail-closed 后，旧内容必须移出可访问树；不得只把它变灰后继续读出。

### 4.3 推荐用户文案

| 条件 | 主文案 | 辅助内容/动作 |
| --- | --- | --- |
| 新鲜且非刷新 | 不新增状态文案，直接显示内容 | 可在已有“更新时间”位置显示 `sourceUpdatedAt`。 |
| 陈旧且刷新中 | “正在显示最近数据，并获取最新内容。” | “数据更新于 …”；内容保持可用，无重复刷新按钮。 |
| 陈旧且刷新失败、仍可降级 | “正在显示最近数据，暂未更新。” | “数据更新于 …”；显示受控的“重试更新”以及安全 trace（若服务端标记可重试）。 |
| 首次同步 | “正在首次同步正式数据。” | “你可以继续使用其他区域。”；显示“重试同步”，并按服务端指示自动恢复。 |
| 强一致查询 | “正在查询最新状态。” | 不显示旧状态替代结果；重复查询入口忙碌。 |
| 失效失败 | “业务已提交，最新数据同步待完成。” | “请勿重复提交”；提供“重试同步”，展示安全 trace。 |

文案可以按区域名具体化，但不得改变上述事实含义；面向业务用户不显示 `fresh_hit`、`stale_hit`、`miss_syncing`、`bypass_strong` 等内部术语。

## 5. 主要用户流程

### Flow A — P0 新鲜热态 `fresh_hit`

1. 已授权用户进入工作台，页面并发请求五个 P0 operation。
2. 页面首次渲染立即保留各区域标题和非数据导航，并把等待状态归属到对应区域；整页不使用阻断遮罩。
3. 新鲜快照在 2 秒内返回。每个成功区域直接显示正式数据，清除 `aria-busy`；初始成功不逐区播报，页面只合并宣布一次“工作台数据已加载”。
4. 无数据的成功响应进入真正的 empty，不被视为缓存 miss，也不触发额外读取。
5. 仅五个 P0 operation 可据此形成“2 秒”验收结论；用户界面本身不展示性能认证标签。

### Flow B — 陈旧但后台刷新 `stale_hit`

1. 合规快照已超过新鲜窗口但未超过最大陈旧窗口，服务端立即返回它，并报告 `dataStale=true`、`sourceUpdatedAt` 和 `refreshing`。
2. 区域在 2 秒内显示内容，同时显示“最近数据”语义和来源时间。若 `refreshing=true`，说明正在获取最新内容；用户无需等待，普通阅读和无冲突操作仍可继续。
3. 相同资源仅有一次后台刷新。界面不得因为多个依赖面板而显示多个会产生重复请求的刷新动作。
4. 刷新成功后，页面只重新获取/接收受影响 operation 的新快照，原位更新内容，移除陈旧说明，并通过 polite live region 宣布“[区域] 已更新”；不抢焦点、不滚动页面。
5. 刷新失败但快照仍合规时，保留内容，把说明改为“暂未更新”；若可重试，提供一个区域级重试。快照超过最大陈旧窗口时转 Flow E，不再展示旧内容。

### Flow C — 真正冷启动 `miss_syncing`

1. 进程刚启动/重启或扩容，且没有持久业务快照。可缓存 operation 在 2 秒内返回 `miss_syncing` 和安全 trace；页面不得继续以普通 loading 等待到 504。
2. 对没有可读内容的所有者区域显示明确的“首次同步中”状态，保留区域标题和页面其他已可用区域。正式 remote 模式不得用静态演示数据填充这些区域。
3. “首次同步中”是可恢复状态，不是空数据，也不是新鲜成功。它提供键盘可用的“重试同步”；同一 operation 的重复入口共享忙碌状态。
4. 自动恢复只服从服务端提供的 `retryAfterSeconds`、刷新完成信号或等价的受控重试指示：每个 operation 同时最多一个前台重读；页面隐藏、路由离开或 operation 已有请求时不再发起。若没有服务端重试指示，客户端不自创固定轮询频率，只保留手动重试。
5. 自动重读仍返回 `miss_syncing` 时，继续显示非阻塞的同步说明和下一次服务端指示，不把状态表现为无限旋转。成功后原位进入 fresh/empty；失败后进入 stale（若有合规快照）或 error。

### Flow D — 强一致查询 `bypass_strong`

适用于 PRD 已分类的 9 个 `S-COR` operation，以及审批提交后状态、写入结果和权限变更确认。

1. 用户进入/触发最新状态查询时，结果区域立即显示“正在查询最新状态”，旧结果不得冒充本次结果；如需保留上下文，只能明确标记为“上次查询结果”。
2. 查询绕过陈旧快照，重复查询控件在请求进行时禁用。页面其他无关区域保持可用。
3. 2 秒内必须已经给出明确的请求中反馈，但不承诺真实飞书查询在 2 秒内完成；不得把长等待伪装成 P0 性能成功。
4. 成功时替换为最新状态并宣布结果；空结果按业务空语义展示；失败时显示错误、可重试动作和安全 trace，不回退到陈旧状态。
5. 用户重试只重发该强一致查询，不触发普通页面全量刷新。

### Flow E — 上游失败与自动恢复

1. 刷新遇到超时、限流或暂时不可用时，若有合规快照，按 Flow B 降级；不得清空仍可用内容。
2. 无合规快照或快照超过最大陈旧窗口时，在 2 秒内显示“数据暂不可用”，错误类别使用安全、可理解的业务文案，并提供 retryable 时的“重试”。
3. `429` 或其他带 `retryAfterSeconds` 的结果显示剩余等待语义，等待期间禁用重复重试；到期后允许一次自动恢复。无服务端指示时不进行紧密轮询。
4. 重试只覆盖失败的 operation。成功区域、用户输入、筛选条件、滚动位置和当前焦点不被重置。
5. 用户发起的重试成功后宣布区域已恢复；失败时保留重试入口和 trace，不能把原请求永久留在 loading。

### Flow F — 写入成功但失效失败

1. 飞书业务写入已经成功，但缓存失效未完成时，动作结果不得显示普通“提交成功”。显示“业务已提交，最新数据同步待完成”，以及“请勿重复提交”。
2. 原提交按钮保持不可重复提交，或转为只执行原幂等结果查询；后续动作必须复用同一幂等语义。用户可用动作是“重试同步/检查最新状态”，不是“再次提交”。
3. 受影响读取区域移除写入前快照并进入“正在查询最新数据”或明确不可用；未受影响区域继续可用。
4. dirty fence 已建立但清除失败时，重试只重放失效/强制回源。dirty fence 也失败时，受影响区域 fail closed，显示“最新结果暂无法确认”；不得显示旧内容。
5. 自动重放成功后，相关区域按强一致路径获取最新状态，再显示最终结果；失败时保留安全 trace 和可恢复说明。界面不承诺回滚已经提交到飞书的业务写入。

### Flow G — 权限拒绝

1. `401/authentication-required` 进入既有登录流程；`403/permission-denied` 表示已登录身份缺少当前内容权限，两者文案与动作必须分离。
2. 权限拒绝发生时，立即清除该 operation 所有私有内容、上次结果、陈旧快照和自动重试计划；不得回退到其他身份或公共快照。
3. 局部权限拒绝只替换所属区域，未受影响区域仍可用。`COM-002` 拒绝时只保留品牌、当前安全路由和主内容入口，不展示未经确认的个性化菜单。
4. permission-denied 不自动重试。只有产品已经配置的授权/支持入口才可展示；没有证据时不发明申请权限链接。
5. 权限或身份变化后，由新的用户动作/会话重建重新读取；旧身份数据不得在过渡阶段闪现。

## 6. 必需状态合同

以下状态适用于每个有远程读取所有权的区域；新增的性能状态是这些基础状态的内容变体，不新增页面。

| 基础状态 | 触发 | 可见内容与允许动作 | 恢复/自动行为 | 可访问性合同 |
| --- | --- | --- | --- | --- |
| `normal / fresh` | 成功返回，`dataStale=false`。 | 展示正式内容和既有操作；可展示来源时间，不显示阻断提示。 | 无需重试。预刷新不得让区域回到阻断 loading。 | 保留既有标题与阅读顺序；初始并发成功合并播报一次。 |
| `normal / stale-refreshing` | 成功返回，`dataStale=true` 且 `refreshing=true`。 | 展示最近数据、来源时间和“正在获取最新内容”；普通阅读可用。 | 后台自动刷新；不提供会制造重复请求的并列刷新按钮。 | 区域可设状态说明，但不因后台刷新持续重复播报；更新完成时播报一次。 |
| `normal / stale-not-refreshing` | `dataStale=true` 且无在途刷新，通常为刷新失败/退避。 | 展示最近数据、来源时间和“暂未更新”；可重试时显示一个重试动作。 | 遵循 retryAfter；重试只作用于 owned operation。 | 状态文案与内容标题关联；不能只用颜色/图标表示陈旧。 |
| `loading` | 初次请求尚未在 2 秒内落入业务终态，或用户重试正在进行。 | 保留区域标题；有合规旧内容则保持可读并标出其状态，否则显示局部 pending。无关操作可用。 | 普通可缓存读取必须在 2 秒内转 fresh、stale、miss_syncing、empty 或 error；强一致读取可继续，但始终显示其明确查询中反馈。 | `aria-busy=true` 只用于所属区域；polite status，不抢焦点。重复触发控件原生 disabled。 |
| `loading / miss-syncing` | 真正冷启动且无合规快照，服务端返回 `miss_syncing`。 | 显示“首次同步中”、安全 trace（可折叠/次要）和“重试同步”；不显示演示数据。 | 服务端指示下自动重读；否则手动重试。用户可离开页面。 | 作为稳定的 status 而非无截止的 spinner；自动恢复不移动焦点，完成后播报一次。 |
| `loading / strong` | 强一致 operation 在途。 | 显示“正在查询最新状态”；旧值只可明确标为上次结果，不能作为当前结果。 | 禁止重复查询；完成后 success/empty/error。 | 发起控件暴露 busy/disabled；结果区 `aria-live=polite`。 |
| `empty` | 正式源成功且业务结果确实为空。 | 显示与区域有关的“暂无…”；保留有意义的筛选重置或导航，不显示错误重试。 | 空结果在 TTL 内复用；不因 0 条自动击穿缓存。 | 一次性宣布“[区域] 暂无内容”；不使用 alert。 |
| `error / no-fallback` | 无合规快照、超过最大陈旧窗口、强一致失败或非权限终态错误。 | 移除不合规内容；说明暂不可用，显示 retryable 时的重试和安全 trace。 | 重试只请求失败 operation；限流按服务端时间恢复。 | 初次非用户触发错误用 polite status；用户触发动作失败或会造成结果误解时用 alert。错误不能只靠 trace 解释。 |
| `error / invalidation` | 业务写已提交，但 dirty fence/缓存失效/重放未完成。 | 明示“业务已提交，最新数据同步待完成”和“请勿重复提交”；只提供同步/查询最新状态。 | 复用幂等结果，只重做失效；相关旧快照不可读。 | 动作结果用 assertive/alert 一次性宣布；焦点规则见第 8 节。 |
| `disabled` | 功能配置禁用、依赖未就绪、同一 operation 已有请求、限流倒计时或 fail-closed。 | 控件呈现真实不可操作语义，并有原因；页面其他功能不受影响。 | 仅在依赖满足/请求结束/倒计时结束后恢复；禁用不得触发飞书读取。 | 使用原生 `disabled` 或等效 `aria-disabled` 加事件阻止；说明通过 `aria-describedby` 关联。 |
| `permission-denied` | 已登录身份被 403 拒绝。 | 清除该区域的私有/陈旧内容，说明当前账号无权查看；无已批准支持入口时不提供虚构动作。 | 不自动重试，不回退其他缓存。 | 局部拒绝宣布一次且不抢焦点；整页访问受限时聚焦可编程标题。 |

`partial` 是页面汇总，不是把所有区域改为 error：成功区域按自己的 fresh/stale/empty 状态展示，失败区域按上述 error/permission 状态展示；页面级重试只请求 `retryScope` 中的 operation。

## 7. 2 秒反馈与时间行为

1. 可缓存 P0 请求从页面发起计时。等待状态应在请求开始时立即可感知；不等到 2 秒才显示反馈。
2. 到 2,000ms 时，P0 所有者区域必须已经是 fresh、stale、miss_syncing、empty 或 error 之一；不得仍只有不说明原因的 spinner。
3. 初始并发读取用一条页面汇总 announcement；2 秒内各 operation 的终态在视觉/语义上归属各自区域，避免五条 live announcement 同时打断用户。
4. 强一致请求不受“2 秒完成”承诺约束，但 2 秒内必须保持明确“正在查询最新状态”并允许用户继续使用无关区域。
5. 显示时间使用绝对时间。可选的相对描述不能替代 `sourceUpdatedAt`，也不能把来源时间说成请求耗时。

## 8. 键盘、焦点与 ARIA live 行为

1. 每个“重试”“重试同步”“查询最新状态”都是语义明确的原生按钮，位于其说明之后的逻辑 tab 顺序；同一 operation 在途时所有重复入口同步禁用。
2. 常规加载、后台刷新、自动恢复和 stale→fresh 更新均不移动焦点，不滚动页面，也不打断正在输入的搜索词。
3. 用户激活重试后，焦点保留在按钮。若成功后按钮从 DOM 移除，将焦点移到该区域现有标题（临时 `tabindex=-1`）并宣布“[区域] 已更新”；若失败后按钮仍存在，焦点保持其上并由关联的 alert/status 说明结果。
4. 用户提交写操作后出现 invalidation failure，应把焦点移到一次性的动作结果标题/摘要；摘要必须先说明“业务已提交”，再说明“同步待完成”，防止用户再次提交。
5. 初次加载整页权限拒绝或整页不可用时，聚焦状态标题一次；局部权限拒绝和局部错误不抢焦点。
6. 区域容器使用 `aria-busy`，不能因一个 operation 在途把整个 `main` 标为 busy。读取内容仍可用时，不对整个区域使用 `inert`。
7. 页面汇总与常规区域更新使用 `role=status`、`aria-live=polite`、必要时 `aria-atomic=true`；写后失效失败、用户触发的强一致失败等需要立即阻止误操作的结果使用 `role=alert`/assertive，但每个事件只播报一次。
8. live 文案不得播报 trace、缓存策略、内部命中代码或每次自动轮询。trace 作为可见补充文本，供用户向支持人员提供，不作为错误的唯一解释。
9. 用户开启 reduced motion 时，等待和刷新状态仍以文本表达；动效停止不得隐藏进度语义。
10. 状态、陈旧、权限和错误必须可由文字识别，不能只依靠颜色、图标、位置或旋转动画。

## 9. Web 响应式交互要求

### 宽屏 Web

- 保持现有壳层、导航和多面板信息架构。状态说明置于其所有者标题/内容附近，页面汇总不替代分区状态。
- 多个 `WB-001` 面板可各自说明不可用/陈旧，但共享一次 operation 重试和 busy 状态。
- 用户可在一个区域刷新时继续使用其他面板、导航和筛选。

### 窄屏响应式 Web

- 仍是 Web，不声称 uni-app/原生移动端支持。
- 面板按现有内容顺序单列/重排；每个状态说明必须紧跟其区域标题，不能集中到用户已看不到的页面顶部。
- 陈旧说明、来源时间和恢复动作按“状态 → 时间 → 动作”的阅读顺序换行；不能把关键文案只放在 hover tooltip。
- 固定/粘性提示不得遮住当前焦点。重试控件保持可见、可触达，触控可用不取代键盘可用。
- 导航权限加载/拒绝时，窄屏菜单只能显示安全导航；关闭/返回主内容的控件始终可用，焦点陷阱沿用现有 shell 行为。

### 未声明平台

uni-app、原生 iOS/Android、小程序未声明，因此不设计、不实施、不验收；响应式 Web 在窄屏可用不等于移动端产品支持。

## 10. 内容与隐私规则

1. 用户可见诊断仅限：区域/operation 名称或 ID、可理解的错误类别、安全 trace、来源时间、服务端允许展示的重试等待；不显示令牌、Cookie、Authorization、凭据、原始响应、手机号、邮箱或其他未脱敏身份信息。
2. 正式 remote 模式下，首次同步、无快照、权限拒绝或 fail-closed 都不能回退本地演示数据；若产品环境明确处于 mock 模式，应继续清楚标注为本地演示，不能与本任务的飞书状态混合。
3. “最近数据”“首次同步”“最新状态”含义固定，不能互换：最近数据是合规陈旧快照；首次同步是无快照；最新状态是强一致真实查询结果。
4. 限流、上游不可用和超时用面向用户的简短文案；底层 HTTP 状态只用于安全诊断，不直接替代内容说明。

## 11. 交互验收场景

1. 五个 P0 新鲜快照在 2 秒内分别填充所属区域；页面仅合并播报一次初始完成，无演示数据闪现。
2. 任一 P0 返回 stale + refreshing：内容可读、时间准确、提示刷新；成功后原位转 fresh，不移动焦点。
3. stale 刷新失败但仍在窗口：保留内容并显示“暂未更新”；超过窗口后旧内容从可访问树移除并出现可重试错误。
4. 真正冷启动：2 秒内显示 `miss_syncing` 对应的“首次同步中”和手动重试；服务端指示下自动恢复，成功后不整页重载。
5. 八路并发命中同资源时，页面可以有多个消费者，但只表现一个 owned operation 的刷新/重试状态，不产生重复用户动作。
6. 强一致查询超过 2 秒：持续显示“正在查询最新状态”，不显示陈旧结果为当前结果；失败后只重试该查询。
7. 写成功、失效失败：不出现普通成功；明确已提交、禁止重复提交、旧快照不可读，重试只做同步/最新状态确认。
8. 403：立即清除所属私有内容，不自动重试、不跳 OAuth；401 进入既有登录流程。
9. 空结果：显示真正空状态并在 TTL 内复用，不显示首次同步或错误。
10. 键盘从重试发起到成功/失败均有确定焦点；live region 不因五个 P0 和自动重读形成播报风暴。
11. 窄屏 Web 中状态说明与所属标题相邻，恢复控件无需横向滚动可达，焦点不被粘性提示遮挡。

## 12. 设计评审检查点与开放问题

### 设计批准前需确认的交互决定

1. 以 operation 所有者区域为状态边界，保留页面部分可用；初始并发只做一次汇总播报。
2. `dataStale`、`sourceUpdatedAt`、`refreshing` 按第 4 节形成唯一内容语义；正式用户不看到内部 cache status 名称。
3. 冷启动采用稳定、可恢复的“首次同步中”，自动恢复只遵循服务端提示，不由浏览器自创紧密轮询。
4. 强一致查询不回退陈旧快照；超过 2 秒时继续显示明确查询中，但不宣称性能达标。
5. 业务写已提交但失效失败时，不显示普通成功，不允许重复业务提交，只允许重试同步/查询最新状态。
6. 403 清除相关私有内容且不自动重试；401 与 403 使用不同路径。

### 实施期需用证据关闭的问题（不改变已批准范围）

1. 响应合同需要为每个 operation 提供可聚合的 `refreshing`；若字段名或承载层不同，必须证明其语义与第 4 节一致，不能只由前端根据 `dataStale` 猜测。
2. `miss_syncing`、限流和后台刷新完成的服务端重试指示/事件载体需在实现证据中明确；若无提示，交互固定为手动重试，不发明固定轮询周期。
3. 现有产品没有已批准的权限申请/支持目的地；在出现证据前，permission-denied 只解释状态，不新增链接。
4. 需验证每个 P0 operation 到现有区域的映射、每个区域的标题/焦点目标，以及 remote 模式下不存在静态演示数据被误认作飞书结果。

本文件仅作为 UX/交互设计输入。它不批准视觉设计，不改变 `task.json`，也不推进任务状态。
