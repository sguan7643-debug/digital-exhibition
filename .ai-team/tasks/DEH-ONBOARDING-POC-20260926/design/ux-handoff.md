## 2. 设计目标与不可扩张边界

为已授权 Web 用户建立一条连续、可恢复、可核验的 T005 海能Work上线申请路径：

1. 从应用中心或个人中心找到入口。
2. 在 `/apps/onboarding/apply` 使用真实飞书目录与字典填写申请，真实上传图标和附件。
3. 以稳定 attempt 提交一个真实飞书审批实例和一条对应申请记录。
4. 提交成功后进入 `/apps/onboarding/status?applicationId=<applicationId>`。
5. 在无 query 的 `/apps/onboarding/status` 查看当前用户自己的 `APP_ONBOARDING` 列表。
6. 在详情进入时自动同步一次，并可手动刷新同一实例的审批状态。
7. 在详情中核验真实图标、附件、申请字段、实例与同步时间。

不可扩张边界：

- 不提供审批人审批操作页、跨用户运营总表、代提交、批量处理、实时推送或持续轮询。
- 不重做 RPA 或其他应用类型流程；现有非 T005 行为不属于本 UX 变更。
- 不新增 uni-app 行为，不定义视觉样式。
- 不把受控 POC 准备、schema 管理、TEST_ 数据准备或清理工具暴露为匿名或普通用户管理页面。
- 不以 fixtures、前端硬编码、拦截请求或模拟状态替代真实 POC。

## 4. 信息架构与路由合同

### 4.1 入口

| 来源 | 入口名称 | 目标 | 行为 |
| --- | --- | --- | --- |
| 应用中心页头 | 应用上线申请 | `/apps/onboarding/apply` | 进入 T005 申请表单。 |
| 应用中心页头 | 我的申请 | `/apps/onboarding/status` | 进入当前用户上线申请列表。两个入口在同一页面操作区内，键盘顺序先“应用上线申请”，后“我的申请”。 |
| 个人中心快捷入口 | 我的申请 | `/apps/onboarding/status` | 替换未落地的 `/profile/todos` 目标。 |
| 个人中心“我的待办 / 申请进度”中的上线申请项 | 申请标题 | `/apps/onboarding/status?applicationId=<applicationId>` | 仅 `APP_ONBOARDING` 项使用本详情路由；链接文本包含应用名称和申请状态上下文。 |

入口是否可见遵循已有用户权限投影；不能只在前端隐藏。直接访问时仍由服务端校验有效会话、当前用户归属和读取权限。

### 4.2 统一状态路由

- `/apps/onboarding/status`：无 `applicationId` 时只呈现当前用户的 `APP_ONBOARDING` 列表。
- `/apps/onboarding/status?applicationId=<合法值>`：呈现该申请详情。
- `applicationId` 是用户可见路由主键；`instanceId`、`resourceId` 是详情数据，不作为详情选择 query。
- query 缺失代表列表，不代表“尚未申请”的单条状态。
- query 格式非法、申请不存在或不属于当前用户时，不读取或呈现业务内容；显示统一的安全受限结果，并提供“返回我的申请”。文案不区分“不存在”和“属于他人”。
- 从详情返回列表时恢复原列表滚动位置和触发链接焦点；直接打开详情时，“返回我的申请”进入列表首部。

### 4.3 页面层级

1. 应用上线申请
   - 页面标题与说明
   - 依赖/权限状态
   - 申请人身份
   - 应用基础与 T005 详情
   - 授权用户与授权部门
   - 图标与附件
   - 提交与恢复反馈
2. 我的申请列表
   - 页面标题与“发起申请”入口
   - 当前用户上线申请列表
   - 列表级状态与恢复动作
3. 申请详情
   - 返回列表与页面标题
   - 规范审批状态、当前节点、最近同步时间与刷新
   - 申请/应用标识与表单信息
   - 授权范围
   - 图标与附件
   - 提交、完成、退回信息

## 5. 核心用户流程

### 5.1 从入口到申请表单

1. 用户在应用中心选择“应用上线申请”，或从列表空态/页头选择“发起申请”。
2. 路由进入 `/apps/onboarding/apply`，焦点进入主内容标题；页面并行读取当前会话、组织、人员、应用类型和业务域。
3. 读取期间表单保留结构但相关控件不可操作，不显示 fixtures 或硬编码候选项。
4. 数据可用后，申请人以当前授权会话身份为准。页面可展示申请人和所属组织，但不得允许选择另一租户身份冒充申请人。
5. 用户选择/确认 T005 所需真实字典数据并填写表单。若 POC 受控准备已写入 TEST_ 字典记录，它们按真实接口结果出现；页面不得自行注入 TEST_ 选项。

### 5.2 图标和附件上传

1. 用户选择图标：最多 1 个，仅 PNG/JPEG/WebP，最大 5MB。
2. 用户选择普通附件：最多 3 个，单个最大 20MB，仅 PDF/DOCX/XLSX/PNG/JPEG。日常表单附件可选；真实 POC 验收必须至少上传 1 个允许类型附件。
3. 选择后先显示“待校验/上传中”而不是“已上传”。服务端交叉校验扩展名、声明 MIME 和文件特征/魔数，并计算 SHA-256。
4. 单文件成功后显示文件名、大小、类型、上传状态和“移除”。失败只影响该文件，显示服务端可行动原因和“重试此文件”。
5. 明确拒绝 SVG、HTML、脚本、可执行文件、ZIP/RAR/其他压缩包和所有未列白名单类型；不保留成功上传记录。
6. 上传中禁止提交和重复上传同一项；其他已填写字段保持可编辑。
7. 提交前移除文件时解除待提交关联，并进入可重试清理；读屏宣布“已移除 <文件名>”。
8. 页面、URL、日志、DOM 可见属性和错误文案均不得包含 tenant token 或原始 file token。

### 5.3 校验、提交与幂等恢复

1. 用户激活“提交审核”。客户端执行格式与必填校验；服务端重复执行全部业务、安全和权限校验。
2. T005 至少要求：真实当前申请人、应用名称、应用编码、应用类型、业务域、适用用户、适用部门和图标；现有 T005 表单合同内的其他必填字段继续生效，不在本 UX 中放宽。
3. 校验失败时不发送创建审批请求。页面顶部给出错误摘要，逐项关联字段；焦点移到第一个无效字段，字段错误与控件通过可访问描述关联。
4. 第一次有效提交创建一个稳定 attempt，并冻结其业务键、幂等键、上传关联和表单快照。在结果确定前，重复点击、页面内重试、网络超时重试和首次投影修复都使用同一 attempt。
5. 提交中保留提交按钮焦点，按钮以忙碌且不可重复激活的状态呈现；表单标记忙碌，读屏只宣布一次“正在提交申请，请勿重复操作”。
6. 明确成功必须返回/恢复唯一 `applicationId`；立即以替换或站内导航进入 `/apps/onboarding/status?applicationId=<applicationId>`，详情显示同一申请。不得先停留在泛化成功页，也不得以 `instanceId` 组成详情 URL。
7. 实例已创建但响应丢失、超时或首次投影失败属于“结果待确认”：保留所有字段、上传关联和原 attempt；显示“继续确认提交结果”。该动作查询/修复原 attempt，不创建新 attempt。
8. 只有服务端明确确认未创建实例和申请时，才进入“明确失败”：保留表单，允许用户修正后创建新 attempt，并启动孤立上传清理。
9. 如果申请已持久化但 `instanceId` 暂缺，仍进入该 `applicationId` 详情；详情显示“暂无审批跟踪编号”，同步操作禁用，不把它视为审批通过。

### 5.4 我的申请列表

1. 用户进入无 query 的 `/apps/onboarding/status`。
2. 服务端从授权会话确定当前用户，不接受客户端传入其他用户 ID 作为过滤依据。
3. 只返回当前用户 `APP_ONBOARDING`，按提交时间倒序；不混入 `APP_USE`、`APP_REUSE` 或其他用户申请。
4. 每项至少呈现应用名称、应用编码、规范状态、提交时间、当前节点（有值时）和详情链接。缺失可选值显示“—”，不能补造内容。
5. 每项的显式详情链接使用 `applicationId`；整行可点击时也必须保留语义等价的可聚焦链接，避免只能用鼠标点击容器。
6. 列表不在本任务中新增搜索、批量操作、审批操作或跨用户筛选。

### 5.5 申请详情、自动同步与手动刷新

1. 详情先读取当前用户拥有的申请持久化数据、附件关联和实例归属。
2. 初次详情读取成功且存在合法 `instanceId` 时，自动对既有实例同步一次。每次进入最多自动查询一次；不做 WebSocket、SSE、定时轮询或隐藏重复完整提交。
3. 自动同步期间保留已读取的详情上下文，状态区标记“正在同步”；不清空旧数据。
4. 自动同步成功后更新同一申请的状态、节点、完成/退回信息和“最近同步时间”，并用礼貌型 live region 宣布结果。
5. 用户可激活“刷新审批状态”。一次激活只查询同一既有实例一次；进行中抑制重复触发并保留按钮焦点。
6. 同步失败时保留最后一次成功数据，明确标注“状态同步失败，以下为 <时间> 的最后成功结果”，提供“重新刷新”。未知上游状态进入错误提示，绝不映射为 `APPROVED`。
7. `instanceId` 缺失时显示“暂无审批跟踪编号”；刷新按钮保持不可激活并提供原因，用户仍可查看已持久化申请和附件。
8. 服务重启或申请超过 24 小时后，详情仍必须从持久化“上架申请”恢复同一实例、当前用户归属、状态和附件上下文；不少于 7 天可查。

### 5.6 真实附件查看

1. 详情显示图标预览或安全查看入口；每个普通附件显示文件名、大小、类型、SHA-256 和上传时间。
2. “查看”只在服务端声明该文件可安全内联预览时出现；“下载”按服务端能力出现。不得通过前端扩展名猜测能力，也不为 DOCX/XLSX 发明在线转换功能。
3. 用户激活查看/下载时，客户端以 `applicationId + fileId + mode` 请求授权。服务端重新校验有效会话、当前申请人归属、文件与该申请的关联，再签发短期、同源、绑定用户和文件的 URL。
4. 查看在受控同源地址中打开，下载沿用同源下载保护；使用新浏览上下文时必须阻止 opener 访问。任何响应均不向浏览器暴露原始 file token。
5. 授权 URL 过期时，页面不复用旧 URL；用户再次激活动作时获取新授权。失败在对应文件行显示，不影响其他附件或详情数据。
6. 附件操作开始、成功交给浏览器、失败或授权过期均通过礼貌型 live region 给出文件名级反馈；失败后焦点保留在原操作或其重试按钮。

## 6. 内容合同

### 6.1 列表内容

- 页面标题：“我的上线申请”。
- 主动作：“发起申请”。
- 列表项：应用名称、应用编码、状态、提交时间、当前节点、详情入口。
- 空态主文案：“暂无上线申请”。辅助文案说明可发起新的应用上线申请；主动作进入 `/apps/onboarding/apply`。
- 状态显示使用规范中文名称，并保留机器值供接口/测试：
  - `PENDING`：审批中
  - `APPROVED`：已通过
  - `REJECTED`：已拒绝
  - `CANCELLED`：已取消

### 6.2 详情内容与顺序

详情至少按以下语义顺序提供内容，顺序同时作为读屏阅读顺序：

1. 页面标题：`<应用名称> 上线申请`；名称缺失时为“上线申请详情”。
2. 状态摘要：规范状态、当前节点、最近同步时间、刷新动作。
3. 标识信息：`businessId`、`applicationId`、`resourceId`、`instanceId`。标识允许换行与复制选择，但不得包含 secret/token。
4. 应用信息：应用名称、应用编码、应用类型、业务域。
5. 申请信息：申请人、提交时间、完成时间、退回原因。
6. 授权范围：授权用户、授权部门。
7. 图标和申请附件：真实元数据与允许的查看/下载动作。

可选值缺失显示“—”；`instanceId` 缺失使用专门的“暂无审批跟踪编号”说明，而不是普通“—”。

### 6.3 状态内容规则

| 审批状态 | 必须表达 | 允许动作 | 发布含义 |
| --- | --- | --- | --- |
| `PENDING` | 审批中、当前节点、最近同步时间。 | 手动刷新、查看附件、返回列表。 | 只存在申请、上传会话和附件关联；不得声称应用已发布。 |
| `APPROVED` | 已通过、完成时间、最近同步时间。 | 手动刷新、查看附件、返回列表；发布投影存在时可核验。 | 只有该状态允许幂等创建/更新应用索引和海能work详情。 |

| 未知/缺失 | 状态暂不可确认，显示最后成功同步时间（如有）。 | 重新刷新、返回列表。 | 绝不按通过处理。 |

## 7. 六态交互合同

## 8. 错误恢复与并发规则

- 所有网络操作有明确作用域：列表读取、详情读取、审批同步、单文件授权、单文件上传、提交 attempt；一个作用域失败不得无条件清空其他成功数据。
- 用户重复激活动作时，同一作用域只保留一个进行中请求。
- 列表错误不等于空；详情同步错误不等于详情读取错误；文件错误不等于申请错误。
- 服务端返回 `401`：转为需要飞书授权；`403`：权限受限且不可普通重试；`404`（详情）：与非本人统一安全文案；`409`：按业务码区分 attempt 恢复、状态冲突或文件状态冲突；`410`（短期文件 URL）：重新申请授权；`429/5xx/超时`：保留上下文并提供同作用域重试。
- 任一重试都复用原 `applicationId`、`instanceId`、文件关联或 attempt；不得通过刷新整页或生成新幂等键规避不确定结果。
- 页面刷新、浏览器前进/后退和服务重启后，都从持久化记录恢复；不得依赖仅存在组件内存的成功状态。

## 9. 权限、隐私与安全交互

- 列表和详情的身份来源只能是有效飞书会话；客户端不提供“查看某用户申请”的参数。
- 列表范围固定为当前用户 `APP_ONBOARDING`。个人中心聚合可以继续包含其他类型，但进入本路由后必须隔离。
- 详情在返回任何字段前校验当前用户归属；附件授权在每次查看/下载时再次校验“当前用户—applicationId—fileId”三者关系。
- 原始 Base token、app secret、tenant token、file token、敏感个人信息不得出现在 URL、页面、浏览器持久化、日志、截图或公开证据。
- 当前授权申请人和真实审批人来自实际会话；TEST_ 字典用户/部门只用于 POC Base 下拉与展示，不能成为租户身份或审批身份。
- 权限被撤销或会话过期时立即清除受保护页面的可见缓存；不能先显示旧内容再覆盖权限提示。

## 10. 键盘、焦点与读屏合同

### 10.1 全局导航

- 保留现有“跳到主要内容”链接和站内 history 行为。
- 新路由进入后焦点到页面主标题；浏览器后退优先恢复来源链接焦点与列表滚动位置。
- 所有动作必须为原生链接、按钮或表单控件；不得只给 `div` 绑定点击。
- 可见焦点遵循现有壳层合同；不在本交接中指定其视觉样式。

### 10.2 表单

- 每个输入都有可感知 label；必填状态不能只由星号表达，星号对读屏隐藏或配合“必填”文本。
- 字段组使用 `fieldset/legend` 或等价语义；适用部门在适用用户之前，部门改变导致已选用户失效时，清空该用户并宣布原因。
- 文件输入有明确用途、允许类型、数量和大小说明；已选文件列表独立于上传触发器并支持键盘移除/重试。
- 提交校验失败先宣布错误数量，再聚焦第一个无效字段；错误摘要中的链接可跳至对应字段。
- 上传、提交或恢复过程中不以自动移动焦点表示进度。

### 10.3 列表与详情

- 宽屏列表使用语义表格时提供 caption、列标题与 `scope=col`；窄屏重排后每项仍保留字段名称，不能只靠列位置解释值。
- 状态文本必须可读，不能只用图标、颜色或装饰符号表达。
- “刷新审批状态”有明确忙碌名称；刷新成功宣布新状态和最近同步时间，状态未变化则宣布“状态未变化，已更新同步时间”。
- 标识、SHA-256 与长文件名允许换行，不制造横向页面滚动；缩略显示时必须有可访问的完整值。
- 附件预览若打开新浏览上下文，动作名称包含文件名；下载动作同样包含文件名。

### 10.4 Live region 纪律

- `role=alert`：权限拒绝、提交失败、详情首次读取失败、阻塞性校验摘要。
- `aria-live=polite` / `role=status`：加载完成、上传结果、提交进行中、同步结果、文件授权结果。
- 同一消息不在全局请求提示和页面局部提示中重复播报；动画和逐字进度不进入 live region。

## 11. Web 响应式交互

- 沿用现有 Web 壳层：窄屏下主内容单列，主导航进入可关闭抽屉；抽屉打开后背景 inert，焦点困在抽屉中，Escape 和关闭动作返回菜单触发器。
- 申请表单：多列字段组按 DOM 顺序重排为单列；标签、说明、控件、错误的阅读顺序保持连续。文件列表在上传区之后，提交动作在所有字段之后。
- 列表：宽屏可用语义表格；容器不足时转为逐项纵向内容组，保持“名称/编码—状态—时间/节点—详情动作”顺序，不通过整页横向滚动保留桌面列。
- 详情：状态摘要与刷新动作在窄屏先后排列；标识、授权范围和附件逐项换行；长 ID、哈希和文件名可断行。
- 所有主要触控动作沿用项目现有窄屏可操作尺寸合同；不因响应式重排改变业务能力、字段必填性、状态含义或安全规则。
- 桌面与窄屏共用同一路由、接口、当前用户过滤和幂等 attempt；响应式只改变内容重排和操作可达方式。

## 13. 预写检查、幂等、七日可查与 POC 证据

### 13.1 首次真实写入四项门禁

以下顺序是不可绕过的服务端/受控 POC 编排门禁，不新增普通用户管理界面：

1. Base 指纹存在、格式合法并精确匹配。
2. 有效授权会话中的真实申请人和真实审批人可用。
3. 独立 POC manifest 的 schema dry-run 无越界、同名异型、必需选项或附件类型冲突。
4. 唯一 runId 的清理台账已持久化。

任一失败时，结构、记录、媒体和审批实例均不得发生首次真实写入。申请页只显示受控、非敏感的“申请服务暂不可用”及是否需要用户重新授权；详细 Base、manifest、runId 和结构信息进入受控 POC 证据，不向普通用户暴露。不得提供“仍然提交”“忽略检查”或用环境开关绕过的交互。

### 13.2 幂等与投影

- 同一 attempt 的业务键、幂等键、申请快照和上传关联在结果确定前稳定。
- 重复点击、超时、响应丢失、首次投影失败、刷新详情或服务重启不得产生第二审批实例、第二申请或重复附件关联。
- `PENDING` 只创建/更新“上架申请”、上传会话和附件关联。
- `APPROVED` 才幂等创建/更新应用索引和海能work详情。
- `REJECTED/CANCELLED` 只更新原申请终态、完成时间和原因，不发布。

### 13.3 七日可查

- 当前 POC 完成证据固定为：真实浏览器即时完整闭环、服务重启后的持久化恢复、可控时钟跨 7 天自动化。
- 第 7 个自然日的真实环境复查为可选、非阻塞观察，不得反向解释为当前 POC 必须等待七天。
- 列表、详情、附件归属和同一 `instanceId` 均需从持久化申请恢复；仅延长内存 TTL 不满足要求。

### 13.4 真实 POC 证据

实现与 QA 至少保留以下脱敏关联证据：

- 两个入口、申请页、提交后详情、无 query 列表和 `applicationId` 详情的真实浏览器截图/录屏。
- 真实目录/字典读取、真实文件上传、提交、列表、详情、同步和附件授权请求；关键请求不得被浏览器测试拦截。
- 同一 runId、businessId、applicationId、resourceId、instanceId、精确 table_id/record_id、上传 ID 与附件 SHA-256 的关联。
- Base 指纹匹配、POC manifest 版本/哈希、dry-run 无越界/冲突、清理台账在首次写入前已创建。
- `PENDING` 到真实终态的前后状态、同一实例、无重复申请/附件/发布记录。
- 服务重启恢复、可控时钟跨 7 天、结构变更前后清单、精确清理结果和不可删除媒体/实例残留披露。
- 自动化与生产构建结果。仅自动化绿灯不能替代真实审批、附件、多维表和浏览器闭环。
