# Product Scope Review

## Verdict

`approved`

最新版 PRD 已处理上一轮四类实质缺口，并将 POC manifest、Base 指纹、TEST 数据精确清理、文件安全、7 天证据和首次真实写入检查落实为前后一致、可测试且不可绕过的范围门禁。现有代码仍有明确实现差距，但这些差距已被正确列为后续设计、开发和 QA 的交付内容，不再被误述为既有保障。提案现已达到用户可批准或拒绝范围的决策就绪状态；本评审本身不构成用户批准。

## Findings

### Finding: 独立 POC manifest 与 Base 指纹已把远端结构写入收敛到最小授权范围

- **Evidence:** `prd.md` F-12、F-18、F-20 明确承认现有通用迁移器会越过本 POC 范围、缺少类型兼容与 Base 指纹检查，因此禁止用于本任务。3.1.C 将结构写严格限定为五张表，并规定非白名单对象、字段或未知动作导致整个计划失败；3.2 给出每张表的完整字段、类型、主键和必需选项，并要求独立 manifest 版本与 SHA-256。`FEISHU_POC_BASE_FINGERPRINT` 必须在 dry-run 和 execute 前精确匹配，AC-05 至 AC-08 分别覆盖缺失/不匹配、越界计划、同名异型、选项/附件冲突、幂等重复执行和变更后再发现。仓库证据也支持“现有实现尚需补齐”的判断：`tools/feishu-schema-migrate.mjs:9,22-25` 使用全局 manifest 且只按字段名判断，`server/feishu-schema-admin-client.mjs:23-33` 尚无 POC Base 指纹门禁。
- **Impact:** 用户授权补表补字段不再等于授权运行全局迁移；错误 Base、额外表、额外字段、改型、删改、影子表和静默兼容均有明确失败条件。现有 Base 快照中的关键字段类型和选项与 3.2 的必需集合可兼容，缺失字段可按只增不删规则处理。
- **Recommendation:** 范围可按当前文本批准。后续设计与 QA 必须把独立 manifest、指纹预检、越界拒绝、类型/选项/附件兼容检查和前后快照作为发布前阻塞证据；不得复用通用迁移器替代。

### Finding: TEST 数据写入、真实身份和精确清理已形成闭合安全边界

- **Evidence:** `prd.md` F-19、F-21、3.1.D 将记录写入限定为九张表，四张目录/字典表仅在已存在且数据不足时新增最少 TEST_ 记录，禁止结构变更、既有记录修改和其他表写入。真实申请人及审批人必须来自授权会话，字典 TEST_ 记录不得伪造租户通讯录身份。每次运行有唯一 runId，首次写入前必须持久化清理台账并登记 Base 指纹、`table_id`、`record_id`、runId、业务键、上传和实例标识。3.3 与 AC-28 要求删除前按精确 `table_id + record_id` 读取并核对 runId，删除后按同一标识复查；禁止按前缀、表名、模糊条件、时间范围或搜索结果批量删除。AC-33、AC-34 进一步验证白名单不可绕过且不得修改租户身份。
- **Impact:** “没有数据就创建数据”的授权已被限制为指定 POC Base 内可追踪的最少验证记录，不会扩张为创建真实组织身份、修改权限或任意写表。清理具有逐记录归属证明，审批实例和媒体无法物理删除时也会披露残留而非伪报零残留。
- **Recommendation:** 范围可按当前文本批准。设计应统一 runId 的序列化规则，并让专用编排器成为九表记录写入与清理的唯一入口；QA 按 AC-28、AC-29、AC-33、AC-34 验证拒绝路径和残留台账。

### Finding: 文件上传与访问安全边界已经固定且可验收

- **Evidence:** `prd.md` F-13、F-22、3.1.E 固定图标为最多 1 个 PNG/JPEG/WebP、≤5MB，普通附件最多 3 个、单个 ≤20MB、仅 PDF/DOCX/XLSX/PNG/JPEG，并明确拒绝可执行文件、脚本、HTML/SVG、压缩包和其他类型。服务端必须交叉校验扩展名、声明 MIME 与文件特征/魔数并计算 SHA-256；浏览器不得接收原始 file token，下载/预览只向当前申请人签发绑定用户与文件的短期同源授权 URL。AC-10 至 AC-12 覆盖成功上传、数量/大小/类型越界、内容不一致和孤立文件清理。仓库当前上传客户端只有 TEST_ 文件名和 20MB 校验（`server/feishu-schema-admin-client.mjs:179-194`），PRD 已正确将强化校验列为实现差距。
- **Impact:** 高风险文件写入不再留给设计阶段任意放宽；上传、持久化、详情访问、失败处理和清理都有服务端边界和验收条件，且不会通过前端提示冒充安全控制。
- **Recommendation:** 无需追加范围决定。设计必须明确 DOCX/XLSX 的 OOXML 容器识别与普通压缩包拒绝方式，并保持 PRD 固定上限；任何放宽应作为新的范围变更重新评审。

### Finding: 7 天持久性与即时真实 POC 的证据关系已经可执行

- **Evidence:** `prd.md` F-23、3.1.F、4.4、状态清单及 AC-25 明确采用“真实浏览器即时闭环 + 服务重启后的持久化恢复 + 可控时钟跨 7 天自动化”作为当前 POC 完成证据，第 7 个自然日真实复查仅为非阻塞观察。AC-27 限定可控时钟只证明持久性，不能替代真实提交、审批、附件和多维表证据。当前 24 小时注册表限制在 `server/feishu-approval-service.mjs:10,156-160,205` 有直接证据，PRD 要求提升到不少于 7 天或从持久化“上架申请”恢复，并明确仅延长内存 TTL 不算满足。
- **Impact:** POC 不必等待 7 个自然日才能完成，同时也不会用单元测试替代真实飞书闭环；服务重启、跨 7 天恢复和同一实例归属均可独立复核。
- **Recommendation:** 范围可按当前方案批准。QA 应保存即时真实闭环、进程重启恢复和可控时钟测试三类独立证据；可选的第 7 天复查不得被重新解释为当前验收阻塞项。

### Finding: 首次真实写入四项门禁已覆盖所有副作用类型且不可绕过

- **Evidence:** `prd.md` 1.3(8)、3.1.H、4.1、状态清单和 AC-35 统一规定：Base 指纹匹配、真实审批人可用、schema dry-run 无越界/冲突、runId 清理台账已创建四项必须按顺序全部通过；任一失败时，结构、记录、媒体和审批实例均不得发生首次真实写入。3.1.H 还明确这些门禁不能通过命令参数、环境开关或手工确认绕过。AC-26 把四项结果纳入真实 POC 证据。
- **Impact:** 结构写安全、验证身份、数据可清理性和真实审批前置条件不再散落为建议，而是统一控制全部远端副作用。权限不足、审批人不可用或结构冲突会如实阻断 POC，不会降级为模拟成功。
- **Recommendation:** 无需进一步修改范围。设计阶段应把四项门禁实现为单一服务端编排状态机，并对每一种失败条件提供“飞书调用次数为零”的自动化证据。

### Finding: 完整业务闭环、真实证据与不部署边界均已决策就绪

- **Evidence:** `prd.md` 3.1.A、3.1.B、3.1.F、4.2、4.3 和 AC-01 至 AC-24 覆盖申请入口、真实字典、T005 提交、稳定 attempt、我的申请列表、本人详情、状态同步及四种审批终态；AC-17 至 AC-19 明确只有 `APPROVED` 才发布。AC-26、AC-27、AC-31、AC-32 要求真实浏览器不拦截关键请求，并关联 runId、applicationId、resourceId、instanceId、精确记录 ID、上传 ID、结构前后和清理证据，自动化绿灯不能冒充真实 POC。`task.json`、`task-brief.md`、`prd.md` 3.4 与 6 一致排除移动端、部署、生产发布、GitHub 推送、PR 和主分支合并。
- **Impact:** 用户要验证的“查看—提交—我的申请—详情—审批进度—终态投影”有唯一解释和完整验收路径；补页面、接口、表、字段及 TEST 数据的授权没有被扩大成生产发布授权。
- **Recommendation:** 用户现在可以决定是否批准该范围。批准后仍需单独完成设计批准，且后续不得把本地 POC 通过表述为已部署或已生产上线。
