# UX/Interaction Handoff

Owner: UX/Interaction Designer

## Sources and Evidence

- Approved PRD: `../prd.md`
- Established behavior: `/apps/onboarding/apply` 现有海能Work提交、加载、错误提示和审批结果行为。
- Service evidence: `src/integration/onboarding-approval.js`、`server/feishu-approval-service.mjs`、`server/feishu-approved-app-projection.mjs`、`server/feishu-safe-test-record-service.mjs`。

## Information Architecture

不新增页面、入口、导航或表单字段。用户仍在 `/apps/onboarding/apply` 完成海能Work申请；本设计只加强提交动作背后的数据一致性。

“适用用户”和“适用部门”继续是用户可见的唯一授权范围输入。飞书表中的“授权用户”和“授权部门”是同一输入的后台投影，不要求用户重复填写。

## User Flows

### 首次提交

1. 用户填写现有必填项、适用用户和适用部门。
2. 点击现有提交按钮。
3. 页面沿用现有提交中状态，禁止重复点击。
4. 服务端创建审批实例并完成“上架申请”投影。
5. 两步均成功后，页面沿用现有成功结果。

### 重试与恢复

1. 若飞书审批实例已创建但投影失败，页面显示现有提交失败信息，不显示成功。
2. 用户按现有方式重试或查询同一审批实例时，服务端复用原审批实例。
3. 若注册记录使用旧投影合同，服务端重新执行投影；若表格记录已存在，则补齐同一记录。
4. 修复成功后返回现有成功结果，不新增第二条申请记录。

## Interaction Rules

- 不增加新的用户操作，也不要求用户理解“投影”“幂等”或“合同版本”。
- 提交成功的交互含义加强为：审批实例已经取得，且本任务要求的上架申请字段已经写入。
- 写入失败必须走现有错误路径；不得先显示成功后静默补写。
- 重试复用同一审批实例和同一业务记录；用户无需重新填写授权范围。
- 只有请求链路再次触发时才修复旧记录，不提供历史批量修复入口。

## Content Behavior

- 保留现有成功文案和错误承载组件。
- 对缺失适用用户或适用部门，继续展示现有校验/接口错误，不新增术语。
- 对投影写入失败，使用服务端现有安全错误消息和 `traceId` 便于排障，不向用户暴露凭据、表ID或内部记录ID。

## Web Behavior

- 桌面和窄屏Web均保持现有表单顺序、键盘操作、提交禁用和焦点行为。
- 请求生命周期保持单次提交状态；修复不新增轮询、弹窗或后台重复请求。
- 页面离开、刷新及浏览器返回行为保持不变。

## uni-app Behavior

未声明；`task.json.platforms` 仅包含 Web。

## Required States

| 状态 | 触发与内容 | 允许操作与恢复 | 焦点/辅助技术 |
| --- | --- | --- | --- |
| normal | 表单可编辑，字段和文案不变。 | 用户填写并提交。 | 保持现有标签、顺序和键盘导航。 |
| loading | 用户提交后进入现有提交中状态。 | 禁止重复提交，等待完整审批与投影结果。 | 保持现有忙碌状态和状态播报。 |
| empty | 本任务不新增空态；表单初始空值行为不变。 | 按现有必填校验填写。 | 保持现有字段关联。 |
| error | 输入缺失或投影失败。 | 保留已填内容，允许按现有方式修正或重试。 | 错误仍通过现有可见文本/提示呈现。 |
| disabled | 提交中或现有条件不满足时沿用当前禁用规则。 | 条件恢复后重新启用。 | 禁用状态不得仅依赖颜色。 |
| permission-denied | 无有效飞书用户授权时沿用当前授权路径。 | 用户完成授权后返回原流程。 | 保持现有授权提示与焦点顺序。 |

## Accessibility Behavior

- 不新增可交互控件，因此沿用现有键盘、焦点、错误关联和状态播报。
- 提交中仍需阻止重复激活，同时不清空用户输入。
- 服务端修复不改变页面DOM顺序或辅助技术可见内容。

## Open Questions and Conflicts

无。已批准PRD明确不修改页面交互和视觉。
